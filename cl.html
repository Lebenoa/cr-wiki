  1. feat changelog serve the commit history at /changelog 2026-08-20 989b772
    Details

    Adds a /changelog page listing the commit history newest first, with the conventional-commit type and scope split off each subject so they can be badged, and the body behind a details toggle. Subjects that are not conventional — the first sixty commits in this history — render whole with no badge rather than being mangled.

    The history is read once at startup, not per request: it only changes when the binary is rebuilt. `git log`'s default layout is parsed instead of a --pretty format string because a format carries % placeholders, and os.execute goes through cmd on Windows, which would expand `%h%` as a variable before git ever saw it. Missing git, or a binary running outside a checkout, leaves the list empty and the page says so.

    Paginated 30 at a time through the same `revealed` sentinel the catalog lists use: 200 commits with their bodies is a third of a megabyte in one response. The Co-Authored-By and Claude-Session trailers are dropped — provenance, not changelog. Linked from the account dropdown.

    Verified: the parsing rules run against this repo's real `git log` output give 200 entries, 140 with a type, no trailer text leaking into a body, no empty subject, and paragraphs split on blank lines. `v -check` is clean and every %changelog_* key resolves in both en and th.

    Not verified end to end: the dev server stopped during this change, so the page was not fetched after pagination landed — see the reply.

  2. feat theme one custom theme that inherits from a preset 2026-08-20 26d1538
    Details

    Adds a "Custom" entry beside the eight presets and a Customize theme editor behind it. The custom theme is not a palette of its own: it names a preset to inherit from and carries per-token overrides on top, so the presets stay exactly as shipped — nothing in this change can edit them, and switching to one strips every override off the root first.

    How the inheritance works: applying `custom` puts the base preset's own data-theme attribute on , so the preflight block supplies the whole palette, then writes the overridden tokens as inline custom properties, which outrank it. Change the base and every override survives; reset a token and it falls back to the base's value with nothing left behind.

    Twelve palette tokens are editable (background through error). The eight --on-* contrast partners are derived from the chosen colour's lightness rather than exposed, so a custom theme cannot end up with unreadable text on a button. Storage is localStorage, like the existing theme choice.

    The variables hold bare OKLCH components because the colour config wraps them as oklch(var(--token)), while speaks hex, so theme_editor.js carries the sRGB <-> OKLab conversion both ways. Rows with no override seed their swatch from the base by reading it off the root with the overrides temporarily removed — a detached probe cannot inherit the default preset, which is the bare html {} block.

    Verified in Chrome: seeds match the real palettes (default #141218, Dracula #282a36/#bd93f9); editing primary to #ff0088 stores "0.6477 0.2626 359.98", derives a dark --on-primary, applies live and survives a reload; reset returns the row to Dracula's purple; switching to Nord clears the overrides and renders Nord's shipped primary; switching back restores base and overrides.

  3. feat treasures search the list by effect, on the server 2026-08-20 ef03ff9
    Details

    /treasures filtered client-side through catalog_filter.js, which compares the search box against each card's name. That could never find an effect: the cards carry no effect text. And the list is paginated 30 at a time, so even a name only matched on the pages already scrolled to.

    The search box is served now. It posts q (and the active tab) to /treasures, which filters and paginates before rendering, so a query runs against the whole catalog. Matching goes through the cached treasure option list — it already holds every effect line for every treasure, in this page's own order (grade, then newest, then name) — with the same term splitting the build picker uses, so both answer "magnet revive" the same way. No new queries: the list is the per-language cache, and only the page's ids are hydrated, through a new select_treasures_by_ids.

    The tab pills carry the query, the infinite-scroll sentinel carries both, and the empty result renders the shared search_no_results string. The other eight catalog pages keep the client-side name filter untouched.

    Verified: "magnet revive" gives 11 treasures on the page and 3 under the Evolved tab; "magnet" gives 69 across three pages, every id appearing once, with the sentinel firing correctly mid-query; the box round-trips through htmx and pushes ?tab=all&q=magnet+revive; a reload of that URL renders the same 11 with the box prefilled; "zzzznope" shows the empty state; the placeholder localizes.

  4. feat builds match every search term in the picker, not the whole string 2026-08-20 be54487
    Details

    The picker compared the search box against each field with one substring test, so a query only ever matched text that sat in a single place. "magnet revive" found nothing: no name and no single effect line holds both words, even though eleven treasures carry a magnet effect and a revive effect side by side.

    The query is now split on whitespace and every term has to appear somewhere in the option, though not in the same place. The fields are joined into one lowercased haystack per option — name, English name and every effect line, blessed included — and each term is checked against it. Multi-word names still work, being two terms the name happens to hold both of.

    Verified: "magnet revive" returns 11 treasures, each showing a magnet line and a revive line (Shortcake Cushion, Iced Sparkling Water Drink, Baby Squirrel's Winter Hat, ...); "revive magnet" returns the same 11, so order does not matter; "cloud boots" still returns Cloud Boots alone; "magnet zzz" returns the empty state; the cookie and pet pickers and the th cross-language search are unaffected.

  7. feat builds list combo partners first in the cookie and pet pickers 2026-08-20 35bb065
    Details

    A combo bonus is the main reason a planner picks one pet over another, and the picker grid is 102 pets and 93 cookies deep, paginated. So when the other half of the pair is already picked, its combo partners now head the grid with a "Combo bonus" pill: the pet picker floats the picked cookie's partners, the cookie picker (lead and relay alike) floats the picked pet's.

    picker_options takes a `partner` id and reorders the filtered list before slicing — pinned selection first, then combo partners, then the rest — and `partner` rides the sentinel URL like `sel` does, so the pages stay a clean cut of one stable ordering: all 4 pet pages with both a pin and a partner set still yield 102 unique ids. The ids come from a new database.combi_partner_ids, which reads the pairing table and nothing else (get_combi_bonus would also resolve names, sprites and effect text the picker has no use for).

    Verified in Chrome: /builds/new?cookie=4 opens the pet picker on Holiday Stocking and Merry Hat, both badged; ?pet=13 opens the cookie picker on Kaymak Cookie, badged, in the lead and relay slots alike; a search that keeps a partner keeps its badge; no partner means no badges; the pill localizes (th: โบนัสคอมโบ).
